# 成熟团队如何做需求分析：方法调研

Last updated: 2026-09-27

服务决定：现有分析是否足以进入任务与信息结构设计，以及还需要明确哪些交付决定。本文是方法参考，不新增功能、研究关卡或固定工期；现行结论仍见[需求分析](../product/needs-analysis.md)。

## 一手案例

以下为团队公开实践或官方指导，核对日期为2026-09-27；不是行业随机样本，也不能证明采用某方法一定成功。

| 来源及性质 | 公开做法 | 可借鉴之处与适用限制 |
| --- | --- | --- |
| [GitLab 产品开发手册](https://handbook.gitlab.com/handbook/product-development/how-we-work/product-development-flow/)：实际团队流程 | 分开问题验证、设计和方案验证；已理解的问题可链接既有研究、反馈等证据；阶段可以交叠，信心充分时允许缩短或跳过无增益阶段 | 先问未知是否影响本次决定。其存量客户反馈不能被我们尚未采集的本地数据替代 |
| [Atlassian PRD 指导](https://www.atlassian.com/agile/product-management/requirements)：团队自述兼方法介绍 | 产品、设计、开发共享用户理解；文档记录背景、目标、假设、故事、设计、开放问题与排除范围；持续更新 | PRD用于协作与取舍。提前穷尽细节、所有团队严格签字后才能工作，被列为反模式；不意味着可以省略必要需求 |
| [Basecamp Shape Up：Write the Pitch](https://basecamp.com/shapeup/1.5-chapter-06)：团队方法书 | 提案交代问题、愿投入的时间、核心方案、易失控部分及明确不做项；用实际项目展示提案与异步反馈 | 明确投入上限和边界；Pitch已含方案塑形，不等同纯需求调研，也不照搬其周期 |
| [GOV.UK Discovery](https://www.gov.uk/service-manual/agile-delivery/how-the-discovery-phase-works)：政府数字服务规范 | 了解用户任务、现有服务、约束和成功衡量，决定是否值得继续投入下一阶段；也允许停止或通过改善已有服务解决 | 为新服务提供更完整的背景分析参照。其发现阶段不建设服务的规定属于政府流程，不普遍套用到本项目 |

[GOV.UK用户研究说明](https://www.gov.uk/service-manual/user-research/user-research-in-discovery)同时列出既有数据、过往研究、观察和访谈，并要求考虑不同能力与支持需求。桌面材料可以采用，但不能凭一个发起者推断所有人的实际使用方式。

## 综合后的工作方式

以下是对上述来源的综合建议，不是任何单一公司的原样流程。

1. **明确要作的决定。** 是判断新产品是否值得探索，还是改进已有功能？写清目标、约束、谁负责取舍和可投入的范围。成熟团队的方法可学；成熟产品已有的使用数据不能假装我们也有。
2. **理解任务与现有办法。** 用户在什么情境想得到什么结果，现在怎么做，哪里受阻？竞品包括搜索、熟人、表格、原站等替代组合；罗列功能差异不足以证明需求。
3. **把材料变成需求判断。** 区分观察事实、个人诉求与推断，说明证据支持到哪里。已有证据能回答的直接采用；问卷用于需要了解分布的问题，观察用于行为问题，原型用于交互问题，技术试验用于实现未知。
4. **选择本次范围。** 将用户收益、覆盖、证据把握、成本与依赖一起考虑；不必强造打分。写清先做、后做、不做及理由。宽产品愿景与窄实现切片分别表达。
5. **形成可协作的需求基线。** 背景与目标、对象与任务、当前办法与不足、核心需要、范围、关键行为与质量要求、验收、假设与待定项；证据放链接，不重复搬运。产品、设计和工程共同检查，在小团队中也可由同一人分角度审查。
6. **按下一笔投入作验证和交接。** 能进入设计不等于能上线。涉及主要价值或不可逆高成本决定的未知优先处理；可逆细节在设计和试用中修正。新证据确实改变判断时更新基线。

需求分析、可行性判断、方案设计会有交叠，但产出不同：分别回答“需要什么及为什么”“能否在约束下做到”“具体如何做”。查到招生网站证明信息存在；不直接证明学生普遍困难。原型顺利运行证明路径可演示；不直接证明用户受益。

## 对当前项目的对照

| 当前情况 | 判断与建议 |
| --- | --- |
| 已有八部分分析、跨场景资料、替代服务和范围建议 | 内容骨架足够，继续沿用；无需另建一套方法编号或重做背景调研 |
| 过去补证、供给试采、原型检验多次被当成需求分析未完成 | 存在把不同阶段的未知合成统一门槛的问题；9月27日已纠正为可评审基线和条件验证 |
| 主文档里积累多轮历史执行顺序 | 当前结论应唯一且醒目；后续维护宜缩减重复正文、保留证据链接，避免历史待办被误读为现行要求 |
| 首版已有导师科研建议，但整体覆盖多种任务 | 保留两层范围；AIDS用于深例，轻量任务检验共性，不能声称已经证明全部人群需求 |
| 尚无明确人力、投入上限和维护责任的最终决定 | 这些会影响承诺与开发范围；在实施计划中明确，暂不编造工期，不以此阻塞独立的信息结构设计 |
| 已有验收方向，尚无真实收益结果 | 设计时落实所选任务的可观察成功结果；试用再检验效果，不把“页面完成”写成“学生已受益” |

建议区分两个交接点：**进入设计**需要问题、对象、依据、范围建议及主要未知可理解；**进入开发**进一步需要选定切片的关键行为、异常情况、必要质量要求、验收和实现约束足够明确。不存在覆盖未来所有需求的一次性完成。

项目的下一项仍是将当前结论落到任务和信息结构：例如，深任务能发现候选、理解差异与实际经历依据，并自主决定下一步；轻任务能直接找到入口后结束。此处是设计目标示例，不宣称已经通过用户验收。
